又翻到这道木棍题。

它太老了：UVA307、POJ 1011，代码不到四十行，思路一句话就说完。可每次隔两个月重写，剪枝那几行还是像别人写的——`if (!cur || cur + w[i] == len) return false;` 凭什么能在这里直接 `return false`，不翻笔记就说不清 😅

搜索剪枝的思维密度就在这里：**剪枝策略每道题都不一样，换一道就得现想**，背不下来。所以这次不写模板，写这一遍是怎么推出来的，以及我数出来的几组递归次数。

## 题面

> 乔治拿来一组等长的木棍，将它们随机地砍断，使得每一节木棍的长度都不超过 50 个长度单位。
>
> 然后他又想把这些木棍恢复到为裁截前的状态，但忘记了初始时有多少木棍以及木棍的初始长度。
>
> 请你设计一个程序，帮助乔治计算木棍的可能最小长度。每一节木棍的长度都用大于零的整数表示。
>
> **输入格式**：输入包含多组数据，每组数据包括两行。第一行是一个不超过 64 的整数，表示砍断之后共有多少节木棍。第二行是截断以后，所得到的各节木棍的长度。在最后一组数据之后，是一个零。
>
> **输出格式**：为每组数据，分别输出原始木棍的可能最小长度，每组数据占一行。
>
> **数据范围**：数据保证每一节木棍的长度均不大于 50。

```
输入
9
5 2 1 5 2 1 5 2 1
4
1 2 3 4
0

输出
6
5
```

时/空限制 **1s / 64MB**，n ≤ 64，每一节 ≤ 50。题目页上写着总通过 **22 456**、总尝试 **57 279**，通过率 **39%**——中等难度，但四个人里只有一个能过。

## 候选答案

正着搜是搜不动的：先拼哪几节、拼成几根，都是未知数。所以反过来，**枚举答案 L，再验证能不能拼出来**。

两个立刻能收紧的条件：

- <span class="hl-red">答案一定是总长的约数</span>。所有原木棍一样长，k 根就是 `sum = k * L`，L 不整除 sum 时连试都不用试。
- `L ≥ max(w)`。任何一节都比原木棍长的话，它根本放不进去。

于是候选 L 就只有 sum 的约数里、不小于最长一节的那么几个。**从小到大试，第一个能拼出来的就是答案**——这比"二分查找答案"还省事，因为候选本身就少。

顺便把二分这条路堵死。`[2, 2, 2]` 这组：sum = 6，候选 L 是 2、3、6。L = 2 可行（三根，每根一节）；L = 3 不可行（2 拼不出 3）；L = 6 可行（拼成一根）。

<span class="hl-red-bg">可行性对 L 不单调，所以二分不只是「没必要」，而是「会错」</span>：二分查 L = 3 判不可行，往大走，返回 6，而正确答案是 2。

## 搜索顺序

验证就是 DFS：`dfs(u, cur, start)`——已经拼好 u 根长木棍，当前这根长 cur，这一步从下标 start 开始挑下一节。

第一个决定是**先放大的还是先放小的**。两种都试一遍就知道差别：先放最大的那一节，剩下的空间立刻变窄，下一层能放的段数就少；先放小段，坑一直很宽，要凑到很深的地方才暴露凑不出来。

![](/images/wan-ci-di-gui-kan-dao-39-ci/01-order.svg)

*图一：同一根 L = 6 的长木棍，第一节放 5 还是放 2，下一层的分支数差了一截。*

所以排序写成 `sort(w, w + n, greater<int>())`。这不是"习惯上大的在前"，<span class="hl-red-bg">先放大的等于让搜索树最上面的几层去做最硬的选择，错的分支在第一层就死</span>。

## 排列与组合

第二个浪费来自重复。`{1, 3, 5}` 放进同一根长木棍，六种顺序是同一件事，DFS 会老老实实走六遍。

处理办法是给下标加一个单向约束：下一层从 `i + 1` 开始挑，编号只能往后长。排列数量级 `k!` 直接塌成 1。

![](/images/wan-ci-di-gui-kan-dao-39-ci/02-comb.svg)

*图二：六种排列对应同一种填法，保留下标递增的那个，其余不再进入搜索。*

代价是排序。等长跳过（下面第三条剪枝）要靠相邻元素比较，一旦不排序就失效——这两条是绑在一起的。

## 三条剪枝

走完上面两步，剩下的才是"失败之后还能推出去多远"。三条都写在失败的当下：

**① 首根失败 → 整层 return。** 这根长木棍还是空的（`cur == 0`），放这一节下去、搜完发现无解，那么剩下的段也不用再试做"第一节"了。

理由是同构：各根长木棍是等价的，最大的那一节总得放在某根的开头，既然放它开头都无解，换任何一节开头只会更糟。

**② 末根失败 → 回溯。** 这一节放进去正好把当前这根填满（`cur + w[i] == len`），往下搜无解，直接 return。

这一条的直觉是：已经把一根木棍拼完整了、结果后面全崩，说明"这样拼满"本身就是坏的选择；换成别的小段凑满同一根，剩下的碎片只会更零碎，更难配。

**③ 长度相等就跳过。** 同一层里 `w[i]` 放失败，那么后面所有和它等长的段，效果完全一样，跳过去。排序之后它们相邻，一个 `while` 就扫完。

```cpp
for (int i = start; i < n; i++) {
    if (st[i]) continue;
    if (cur + w[i] <= len) {
        st[i] = true;
        if (dfs(u, cur + w[i], i + 1)) return true;
        st[i] = false;
    }
    // ②：作为当前这根的第一节或最后一节都失败 → 整层失败
    if (!cur || cur + w[i] == len) return false;
    // ③：同一层不再试等长的小段
    int j = i + 1;
    while (j < n && w[i] == w[j]) j++;
    i = j - 1;
}
```

## 实测

剪枝到底值多少，光看代码是看不出来的。我把三条逐条打开，数同一份输入上的递归调用次数（逻辑照抄，用 Python 重写只为了加计数器；调用次数和语言无关）。

| 剪枝 | `2 4 4 5 5 5 5 5 5 5`（答案 15） | `2 7 7 8 8 8 8 8 8 8`（答案 24） |
|---|---|---|
| 一条都不用 | 69 864 | 69 265 |
| + 首根／末根失败 | **39** | **102** |
| + 等长跳过 | 39 | 102 |

<span class="hl-red-bg">同一份输入，六万九千多次递归，砍到 39 次</span>——差 1791 倍，而改的只是循环末尾那三行。

![](/images/wan-ci-di-gui-kan-dao-39-ci/03-bars.svg)

*图三：对数刻度。线性刻度下 39 会被画成一条看不见的线。*

有个细节和预期不一样：**第三条（等长跳过）在这两组输入上一次都没触发**，前两条已经把"第一根就填不满"的树砍干净了，轮不到它出手。

这不代表它没用。它省的是"失败发生在中间位置、后面恰好跟着一串等长的段"那种分支，样本只有十根的时候撞不上。我不想为了让它显得重要，去找一组能让它出彩的输入——那更像是先有结论再找证据。

另外看候选表，也能看出二分为什么不成立：

| 候选 L | 递归次数 | 结果 |
|---|---|---|
| 5 | 16 | 不可行（2 和 4 都拼不进 5） |
| 9 | 9 | 不可行（2 配 7，7 却凑不出 9） |
| 15 | 14 | 可行（2+4+4+5，剩下六个 5 分两组） |

中间那个 9 夹在两个失败之间，候选的可行性和大小没有关系。顺序枚举是对的，二分找不到这个形状。

## 边界

写的时候有几个地方必须交代清楚，不然代码是"看起来对"：

1. **`len` 从最长的一节开始**，不是从 1，也不是从平均值。
2. **`len == sum` 一定有解**（所有节拼成一根），所以枚举不会死循环。
3. **多组数据**：读到 `0` 结束，每组都要 `memset(st, 0, sizeof st)`。不清空就是把上一组的用过标记带进下一组。
4. **`N` 开到 70**：n ≤ 64，留几格。
5. **剪枝之间不独立**：等长跳过依赖排序，排序又依赖"先放大的"这条策略。
6. 最要紧的一条：**这些剪枝不通用**。换一道搜索题，剪枝的形状要重新看——先问自己"在这棵树里，什么情况下失败是必然可以外推的"，再去写 `return`。

```cpp
#include <iostream>
#include <cstring>
#include <algorithm>

using namespace std;
const int N = 70;

int n, w[N], sum, len;
bool st[N];

bool dfs(int u, int cur, int start) {
    if (u * len == sum) return true;          // 全部拼完
    if (cur == len) return dfs(u + 1, 0, 0);  // 当前这根满了，开下一根

    for (int i = start; i < n; i++) {
        if (st[i]) continue;
        if (cur + w[i] <= len) {
            st[i] = true;
            if (dfs(u, cur + w[i], i + 1)) return true;
            st[i] = false;
        }
        if (!cur || cur + w[i] == len) return false;
        int j = i + 1;
        while (j < n && w[i] == w[j]) j++;
        i = j - 1;
    }
    return false;
}

int main() {
    while (cin >> n, n) {
        sum = len = 0;
        for (int i = 0; i < n; i++) {
            cin >> w[i];
            sum += w[i];
            len = max(len, w[i]);
        }
        sort(w, w + n, greater<int>());

        memset(st, 0, sizeof st);
        while (true) {
            if (sum % len == 0 && dfs(0, 0, 0)) {
                cout << len << endl;
                break;
            }
            len++;
        }
    }
    return 0;
}
```

最后留下的判断其实只有三条：答案的空间被约数压得很小，不用二分；搜索顺序上先强后弱；剪枝的入口永远是"失败的形状"——第一根就失败、最后一根才失败、失败在等长的兄弟上。

下次再遇到搜索题，这套不一定搬得动。可"先问失败能不能外推"这个动作，是可以带过去的。

至于为什么这道题每次都要重想一遍 🤔 大概就是因为树长得不一样，上一次见过的形状这次不一定出现。
