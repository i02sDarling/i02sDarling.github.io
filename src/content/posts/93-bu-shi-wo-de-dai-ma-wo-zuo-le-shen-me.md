最后一通电话是下午四点多，和后端对字段：这个金额传到前端是分还是元，回调重复的时候状态字段会不会连着来两次。

这类电话十一个月里打过很多次，只有最后一次我记得清清楚楚。挂断之后我在椅子上坐了一会儿，意识到手里剩下的东西只有文档了。

第二天写完交接文档，把还开着的 issue 一个个转出去，最后把 `.claude/skills` 打成一个压缩包发过去。包里 **43 个目录**，命名谈不上讲究。

## 一、表单

这条线上我做的主要是**表单**：投前审批、投中付款、投后治理、退出重组，每个节点都是一张要填、要校验、要流转的页面。系统有 PC 版，也有钉钉 H5 版，同一份业务逻辑要活在两个容器里。

用 Formily 之后，页面的主体是一份 schema，字段、组件、校验、联动都写在里面。

```js
// 伪代码，仅示意结构
const schema = {
  type: 'object',
  properties: {
    dealAmount:    { type: 'number', 'x-component': 'MoneyInput' },
    approvalLevel: {
      type: 'string',
      // 金额跨过阈值，审批层级要跟着跳一级
      'x-reactions': (field) => { /* 伪代码 */ },
    },
  },
}
```

真正花时间的是 schema 之外的那一层：自定义事件接口、多级联动、动态模板。这些在引擎里没有现成槽位，得自己扩。扩的时候才明白，**引擎的好处和坏处是同一件事**——它把表单变成数据，你就能批量处理；也正因为变成了数据，任何一处约定不对，同款页面会一起错。

跨端那部分最难写进 schema。PC 和 H5 的差异不在代码里，在「哪一端会先崩」这种经验里：H5 的键盘会把弹层顶上去，PC 的宽表格在钉钉里会横向拖断。这类东西我是被用户截屏指出来才学会的。

## 二、93%

代码生成占比，年初 **49%**，年底 **93%**。

工具没换那么多次，换的是用法。49% 那一段是补全级：我写函数名，它补函数体，我还得盯着，因为它补出来的版本常常看着对。93% 那一段是整页级：先让它读三份东西（需求单、接口文档、一个历史相似页面），再让它按 schema 出整页，我只留改字段和接联调。

差距不在它变聪明了，在<span class="hl-red">我学会了先给它什么</span>。

表单最适合交给它，因为验收标准是可执行的：填一个错的，看它拦不拦；选一笔大额，看审批层级跳不跳。对错当场就知道。

反过来，跨端适配、金额精度、草稿箱的恢复顺序，这几块生成率立刻掉。它们的对错当场看不出来——要等用户在钉钉里滑到那一屏，或者等一笔钱算错一分。

93% 这个数是我按自己的周报口径估的，换成按函数、按 PR 去数，结果不会一样。

## 三、读的成本

生成率高，不等于我懂得多。这两件事经常被混着讲，包括我自己在很长一段时间里。

代价我数得出三条：

1. 读的时间被挪到下一次。它给的整页我要逐段确认，确认它没有顺手改掉一个校验条件。
2. 定位路径变长。出了问题，我没走那段推导，就不知道该往哪儿怀疑。
3. 只懂结果不懂原因。类似的需求再来一次，我还是得问它，因为那层理解没建立起来。

第三条最要命。<span class="hl-red">它不会当场咬你，它咬的是半年后的你。</span>

<span class="hl-red-bg">93% 是产出比例，不是能力比例。</span>

还有一件到现在也没想清的事：这套流程跑顺之后，「我」究竟在哪一环。想不清就先记着，不急着给它一个好听的答案。

## 四、Agent 三条

一年里试过很多写法，稳定下来的只有三条，都是被坑出来的。

**独裁制协作。** 同一个任务只让一个 agent 写，其余只读。多写会互相覆盖，最后合出一个谁也没想过的版本——每一支都合理，合起来不通。

**生成-评价分离。** 写的人和判的人必须是两个上下文。让同一个上下文自评，结果永远是「通过」，因为它知道自己想干什么。

**上下文外置。** 上下文焦虑的解法不是压缩，是外置：稳定的规范进 Skill，临时信息只留这一次。焦虑来自「它会不会忘」，解法是让它不必记住。

## 五、Skill 库

43 个目录，覆盖知识管理和工程效率。结构很土：一个目录一份 `SKILL.md`，几段约束。

```
.claude/skills/
├── deal-approval/   # 投前审批表单的结构与联动约定
├── amount-format/   # 金额精度、千分位、单位统一
└── ...
```

写 Skill 其实是把「我为什么这么做」写下来，逼自己承认有些习惯只是习惯。我给自己定了一条：**声明式优于命令式**——不写「先打开 X 再点 Y」，写「交付物是什么、约束是什么、怎么算通过」。<span class="hl-red-bg">前者只能照着做，后者能被改、能被复用。</span>

团队办过一轮分享，我上去讲过两次。有一次讲完，一个后端同事问这个能不能给他抄一份，那是这一年里我觉得最值的时刻之一 🙃。

## 六、师兄师姐

十一个月里，很多个晚上群里还在对字段。这活很枯燥：确认这个金额是分还是元，确认这个状态会不会重复回调。

我这一年的运气不在 AI 上，在有人愿意把一段核心链路交到我手上。第一周就让我接页面，review 时指出问题也给改法，我要走的时候，他们把「这块以后归谁」一条条写清楚。

<span class="hl-red">在中厂里，最稀缺的不是技术，是有人肯把一段核心链路交给你。</span>

## 七、中厂

劳动合同签在数字马力，业务在另一家公司的系统里。这个结构的好处和坏处，我在实习期就写过一次，现在再看，意思变了。

好处是链路完整、规范现成、有人带，一年多里能见到一条业务从审批到退出的全貌。坏处是很多「为什么这样设计」的答案在另一个会议室，你只能从代码里反推。

当时我把「你写的是别人的系统里的一段」当成限制。现在也说不清它算不算限制——深度确实是从这条边界里长出来的，但<span class="hl-red">边界之外的判断，我一次也没参与过</span>。

## 回顾

两条。

第一，真正留下来的不是代码，是「哪种需求可以交给 AI、哪种必须自己写」的顺序。它写不进简历，但能跟着我去下一个地方。

第二，93% 以后还会涨。重要的不是涨到多少，是我有没有在它涨的时候还留着一段自己写——那一段才是判断力的来处。

压缩包发出去之前，我犹豫过要不要删掉那两个写得最随意的目录，`deal-approval` 和 `amount-format`，里面有一半是给自己看的抱怨。

最后还是留着。下一个接手的人大概会先骂一句，然后打开看看。
