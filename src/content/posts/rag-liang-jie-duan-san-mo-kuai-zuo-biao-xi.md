20 个优化点，一个点配一个 notebook。要记的不是这 20 个名字，是它们各自站在流程的哪一格。

## 一、大模型的两个盲区

大模型本身的知识有两个硬伤。

**第一个是不实时。** 前两天发生的事，模型没训练过就不了解，而且它没有办法自己更新。这一点很直观：一个只读过 2024 年数据的模型，问它本周的新闻，它只能编。

**第二个是企业私有数据拿不到。** 比如在飞书里问「怎么开通会员、怎么升级会员」，这套文档不在训练集里；再比如一家房地产企业记录了今年一整年的销售数据，这些也不可能进模型权重。

两个盲区指向同一个需求：**回答之前，先去取一份外部的资料**。这门技术就是 RAG，检索增强生成。

## 二、双流架构：从闭卷到开卷

RAG 的结构可以说成一条「双流」。

大模型生成之前，先拿用户的问题去向量数据库里找能回答这个问题的背景知识，把找到的内容和原始问题拼成一段上下文，一起传给大模型。

原来的大模型是**闭卷考试**——只凭参数里的记忆答题；现在改成**开卷考试**——资料摆在桌上，照着资料答。

这个比喻不只是修辞，它决定了优化的方向：闭卷考试考的是记忆力，开卷考试考的是**找资料的能力**。所以后面所有的优化，本质都在解决「怎么把正确的那几页翻出来」。

## 三、两阶段：检索与生成

整个系统就两个阶段。

**阶段一是获取背景知识。** 用户来了一个问题，我要拿到正确的知识，因为只有基于正确的知识才可能得到正确的结果。这一步叫「正确的匹配」：用各种策略，让用户的 query 命中库里真正相关的那几块。

像去图书馆查资料——偌大一个图书馆，你怎么做到**既快、又全、又好**地找到与问题相关的参考答案。

**阶段二是生成正确结果。** 假设给一批医学参考资料，没有受过训练的人照样不能给病人看病。资料对了，模型能力不够，答案还是会错。

两阶段的分工很重要，因为它对应简历里两处不同的量化：第一阶段写检索精度从多少提到多少，第二阶段写端到端回答准确率从多少提到多少。**这两组数字不能混着写**，混了面试官一追问就露。

## 四、三模块：离线解析、在线召回、在线生成

系统按时间切成三块。

**离线解析模块。** 文件入库是离线发生的，和用户提问不在同一时间。做企业知识库，是把大量文件先解析、切块、向量化存进库，之后才挂一个对话框。用户提问时，知识库早就建好了。

**在线召回模块。** 用户的 query 进来，先检索，再生成。

这三块的边界，就是后面判断「这个优化值不值得做」的依据：**离线模块慢一点没关系，不影响用户体验；在线模块每多一步，用户就要多等一步。**

## 五、Trash in, trash out

文档处理这一块，一句话就够：<span class="hl-red">垃圾进，垃圾出</span>。

一个成立了十几二十年的企业，知识库里什么都有：图片、表格、流程图、文字混在一起，多模态信息纠缠着。直接解析，很难解准：

- 图片怎么解析？里面的信息怎么读？
- 流程图怎么读？
- 表格表头凌乱，怎么把行列关系还原出来？

所以第一个优化点是：**怎么从各种形态的文档里读出正确的结构化信息**。解析结果错了，后面切块、向量化、检索再精巧，检索回来的也是垃圾。

## 六、六个原子环节，六个病灶

把流程拆到底，其实是六个「原子」环节：文档解析、文本分块、相似度检索、用户查询、上下文组装、提示词构建。每一个环节都有自己典型的病。

| 环节 | 存在的问题 |
| --- | --- |
| 文本分块 | 完整段落被切成两半，只检索到一半就有信息遗漏；表格被拦腰切开，命中下半块时连表头都没有 |
| 用户查询 | 用户往往说不清自己的问题，说不清就很难找到相关信息 |
| 相似度检索 | 语义相关 ≠ 能当背景知识。问「俄乌战争现在怎么样了」，可能召回「伊朗核战争现在怎么样了」 |
| 上下文组装 | 检索回来的内容太长、超过上下文长度怎么处理 |
| 提示词构建 | 检索结果有的相关有的不相关，怎么让它只答相关的；能不能给出引用，告诉用户答案基于哪一段 |

这些病灶不是「理论上可能」，是每次都会撞上的：只要你在真实文档上跑过一次 RAG，这些坑会一个不落地出现。

## 七、把基础流程手写一遍

在谈优化之前，得先有一个能跑的基线。这条线是：**文档解析 → 切块 → 向量化 → 用户查询 → 两两匹配 → 拿到背景知识 → 得出结果**。

```
import fitz  # PyMuPDF
import numpy as np
from openai import OpenAI

def extract_text_from_pdf(pdf_path):
    mypdf = fitz.open(pdf_path)
    return "".join(page.get_text("text") for page in mypdf)

def chunk_text(text, n, overlap):
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunks.append(text[i:i + n])
    return chunks

def cosine_similarity(vec1, vec2):
    return np.dot(vec1, vec2) / (np.linalg.norm(vec1) * np.linalg.norm(vec2))
```

切块的两个参数是 `n`（每块多大）和 `overlap`（相邻两块重叠多少），后面一整篇都在讨论这两个数字怎么定。

向量化用 `text-embedding-ada-002`，输出 **1536 维**。一本《Understanding Artificial Intelligence》切成 **42 个块**。这里很容易忽略的一点是：embedding 返回的不只是向量，还有序号（第 0 块、第 1 块……）和类型，序号就是后面做「取相邻块」「按 metadata 过滤」的抓手。

检索没有用 Milvus，是纯手写：query 也向量化，然后和库里每一个块的向量算余弦相似度，排序，取前 K。

```
def semantic_search(query, text_chunks, embeddings, k=5):
    q = create_embeddings(query).data[0].embedding
    scored = [(i, cosine_similarity(np.array(q), np.array(e.embedding)))
              for i, e in enumerate(embeddings)]
    scored.sort(key=lambda x: x[1], reverse=True)
    return [text_chunks[i] for i, _ in scored[:k]]
```

手写的意义在于理解内部逻辑：Milvus、ES 这类库内部做的事情和这差不多，只是加了**近似最近邻（ANN）**来提速。<span class="hl-red">相似度就是两个向量点积除以它们的模</span>，没有更神秘的东西。

最后一步是组装。系统提示限定「只根据给定上下文回答，答不出来就说没有足够信息」，用户提示把几个 chunk 拼起来、末尾附上问题。

## 八、评估：先有尺子，再谈优化

搭完系统必须配一套评估，否则后面 20 个优化点全凭感觉。

最朴素的做法是让大模型当判官，三个分数：**完全正确 1 分、部分相关 0.5 分、错误 0 分**。给它的输入是用户问题、AI 回答、以及评估集里的标准答案。

评估集本身要有四个字段：

| 字段 | 含义 |
| --- | --- |
| question | 问题是什么 |
| ideal answer | 理想回答是什么 |
| reference | 参考了哪些片段 |
| reasoning | 怎么推到这一步的 |

光看端到端分数也不够，还要拆成两个维度：

- **忠实度（faithfulness）**：有没有基于我给的资料回答，有没有编。
- **相关性（relevance）**：答案和理想回答的相关度是多少。

<span class="hl-red-bg">一个尺子只有一个刻度，你就只能知道「变好了」，不知道「哪一段变好了」。</span>两个维度合起来，才能判断一次改动到底动了哪一环。

## 九、优化的第一原则

20 个优化点听起来像一份打勾清单，实际不是。

第一件要建立的事是**框架性的思路**：不是「今天做 rerank，明天做 rewrite，后天微调 embedding」这种招式堆叠，而是知道**这个优化方案在整个流程里属于什么位置**。

第二件事更难接受：<span class="hl-red">并不是每一种优化方案都能产生正确的结果</span>。后面会反复看到，好几个优化点做完之后分数反而降了——语义分块从 1 掉到 0.5，查询转换跑完发现原始 query 最好，加了意图识别反而不如以前。

所以正确的做法是**从 bad case 出发**：哪里答错了、错在检索还是错在生成，再去那个环节挑方法，做完再跑一遍评估集看值不值得留。

每加一个模块，token 消耗变大、延迟变长、运维成本上升。**加不加，是一个效率和精度的交易**，而不是「上得越多越专业」。

## 十、坐标系

这四个字的用处在于：拿到一个新方法，先问它在哪一格——离线还是在线，检索还是生成，六个原子环节里的哪一个。

离线模块的优化可以奢侈：多调几次大模型、多算几轮相似度，用户看不见。在线模块的优化必须抠：每多一次模型调用，首字延迟就多一截。**同一种方法放在不同格子里，结论可能完全相反**——语义分块在离线做是合理的，放在在线做就是灾难。

后面三篇分别走离线、在线、收尾三段，每一段都会给一个分数，也都会给一次「这个分数是怎么来的」。

数字都绑着当时的模型和文档：《Understanding Artificial Intelligence》42 块、ada-002、1536 维、gpt-4o 与 gpt-3.5-turbo 混用。换一份文档、换一个 embedding 模型，绝对值会变，**但「哪个环节漏了信息」这件事不会变**。
