第一次看到「交付代码就像负债累累」，我以为是说代码写得脏。

## 一句原话

1992 年，沃德·坎宁安（Ward Cunningham）在 OOPSLA 的体验报告里写下这句：

> Shipping first time code is like going into debt. A little debt speeds development so long as it is paid back promptly with a rewrite… The danger occurs when the debt is not repaid. Every minute spent on not-quite-right code counts as interest on that debt.

第一次交付的代码就像背上一笔债。只要尽快用一次重写还清，一点债能加快开发……危险出现在债没还的时候。花在「不太对的代码」上的每一分钟，都算这笔债的利息。

我第一遍读，把 `not-quite-right` 读成了 `bad`。

这两个词差得很远。bad 是手艺问题，not-quite-right 是认识问题：写的时候只知道这么多，代码按当时的理解是对的，只是理解得不够。坎宁安后来解释过，<span class="hl-red">债是「我们还没有弄明白的那部分」，不是代码写得脏。</span>正因为要不断回来改，才更要把代码保持干净。

把「技术债」当成「写得烂」的同义词，从第一步就偏了：一个在说还欠着多少理解，一个在说手艺不行。

## 两笔账

代码为什么像负债，可以拆成两个原因。

第一个是**实现有问题**。有 bug，选了不合适的组件，绕开了本该走的那条路。这笔债是借来的时间：为了先上线，先这么写。

第二个更少被提起：代码本身没毛病，但技术在往前走。三年后框架换了大版本，依赖停止维护，运行环境不再支持那套写法。这笔债不是借的，是**放着的代价**。

## 三笔利息

把「利息」当成一个整体，它就会变成一句口号。拆开之后其实只有三笔，每一次改动都要付：

1. **读。** 改之前得先把这段逻辑读回来，包括它为什么长这样。
2. **改。** 新代码要和旧写法兼容，能绕开的绕开，能不改的不改。
3. **验。** 回归面变大，测试要多跑一遍，手动点的地方也要多一遍。

三笔加起来，是这次改动多花的时间。再乘一个数：这段代码之后还会被改多少次。

<span class="hl-red">债的利息不是按行数收的，是按改动次数收的。</span>

这条一成立，很多争论就没意义了。一个三千行的模块，如果半年没人碰，它一分利息都不付；一段二十行的工具函数，如果每个需求都要进去改一次，它一直在付。用行数衡量债务，等于用贷款金额衡量风险，把还款频率整个漏掉了。

有一处看着矛盾：代码放着不动，技术照样往前走，债在变大。但这份账单不在原地产生，要等某天真的去改、或者要迁移时，才一次性结算。

## 同一个词

「技术债」现在至少装着三种东西，混着用就会互相打脸。

2010 年，Steve Freeman 写过一句更准的话：坏代码不是技术债，是一张没有对冲的看涨期权。他的意思是，如果这段代码以后再也不会被碰，那当时的偷懒就是赚的；真正的问题是「以后会不会被碰」这件事不可预测，而且一旦被碰到，代价不是线性增加，是突然变得很贵——换平台、加合规报表、核心成员离职，都在这一栏。

2011 年，Ovid 补了另一刀：货币债务有还款时间表，技术债没有。银行会按月催，代码不会。「技术债是不是债」这个问题，答案取决于有没有义务。

2014 年，Doc Norton 把界限划得更清楚：真的技术债是干净的、可测的、带着明确学习目标和还款计划的代码；做不到这几条的，只是 cruft——写得烂而且没人打算还。

再往前一步，是坎宁安自己的态度。有共事过的人回忆，他说过后悔造这个词，因为它让人以为债可以一直加：既然第一笔没什么感觉，那再来一点又怎样。他后来更愿意用「机会」这个说法——好的实践攒出机会，机会可以在赶工时花掉，但花完要回到基线，不能掉到基线以下。

<span class="hl-red-bg">同一个词底下装着两种东西：一种是有计划的借，一种是没人打算还的欠。</span>

这两种东西在会议上的说法完全一样，所以永远谈不拢。有人说「先欠着，下个季度还」，有人说「我们从来没还过」——他们说的不是同一笔账。

## 折算

想把债变成一个数字的尝试一直有。SonarQube 的技术债插件会按违规条数折算成工时，再折算成金额，报表上给一个很像财务数字的东西。

2014 年 hello2morrow 那篇批评说得直接：不同违规怎么加权是人为定的，内置规则里很多对可维护性没有可测影响，真正要紧的架构一致性、耦合度、结构合理性，基本没进公式。于是报表上会出现一个精确到小时的数字，它测的是一组约定，不是债务。

## 复现

债的利息算不出来，但可以排序。用 git 的历史做一次粗排，找出「被改得最多」和「同时很大」的文件：

```bash
git ls-files '*.ts' '*.tsx' \
  | while read -r f; do
      n=$(git log --oneline --follow -- "$f" | wc -l)
      l=$(wc -l < "$f")
      echo "$((n * l)) $n $l $f"
    done | sort -rn | head -20
```

输出四列：乘积、变更次数、行数、路径；第一列只是排序键，不是金额。

跑完常见两件事：排在前面的往往不是最长的文件，而是那个每次需求都要进去改的组件；全库最大的文件，可能三年只改过两次。`--follow` 追不到跨文件拆分，所以这个排序只能用来找候选。

## 边界

**一，不碰的代码不付利息。** 把一个三年没人改的模块列进重构计划，是在还一笔不存在的债。判断动作只有一个：它半年内会被改吗。

**二，删代码也有成本。** 调用方、存量数据、权限、报表，任何一项都可能让删除比保留更贵。删不掉的「免费」代码，其实已经变成了接口——这层债不在代码里，在依赖图里。

**三，所有代码都是技术债，不等于少写就对了。** 产品没上线，债是零，收入也是零。债是入场费，不是原罪。

还有一条隐性条件：债的定价取决于谁接手。同一段代码，原作者改是半小时，新人改是两天。团队流动越快，同一笔债的名义金额不变，实际利息越高。

## 判据

**先问频率，再问质量。** 半年不改的，放着；每周都进的，先动手。<span class="hl-red">质量只在「会被读」的地方才产生成本。</span>

**把「借」和「欠」分开记账。** 借的那笔要有还款动作和时间点，欠的那笔要么删掉，要么承认它不会再还——两者都比含糊地挂在待办里强。

这两条都不解决「该不该重构」的争论 🤔 它们只是把争论从「这段代码丑不丑」挪到「这段代码以后还会不会被碰」。前者靠品味裁决，后者可以查。

删掉的代码不产生利息，也不产生功能。

真正被继承下去的，往往不是代码，是当时那份还没想明白。
