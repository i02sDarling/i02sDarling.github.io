离线侧优化做到头之后，剩下的所有问题都指向同一处：query 和答案之间那道语义裂缝。

## 一、真正的核心矛盾

今天几乎所有 RAG 优化都围绕同一个前提：**给当今最强的大模型一份正确的背景知识，它基本都能答对**。

那问题就只剩一个：怎么用用户的 query 找到那份能回答它的背景知识。

难点在于两者的语义并不天然对齐。库里有一块讲「俄乌战争是什么」，用户问的是「以色列和伊朗的战争怎么样了」。两块文本语义很近——都是战争、都是地缘冲突、句式都类似——但**它们半毛钱关系没有**，拿俄乌那段去回答中东，就是纯粹的错误。

同理，用户问「今天是星期几」，向量检索可能召回「伊朗核问题现在怎么样了」，因为都是疑问句、都带时间感。

所以「语义相似」和「能当背景知识」是两件事。<span class="hl-red">前者是检索系统会算的东西，后者才是用户真正需要的东西</span>。这一篇的所有手段，都在试图补上这段差。

## 二、QA 对：把 Q-K 匹配换成 Q-Q

第一个补法很朴素：既然「问题」和「文档块」长得不像，那就在入库时**把文档块加工成问题的样子**。

做法是让大模型读每个块，生成几个「这块内容能回答的问题」。

```python
system_prompt = "你是一名擅长从文本中提炼关键信息并生成相关问题的专家。请只用中文，根据给定文本生成可以用该文本直接回答的简明问题，聚焦于核心信息和重要概念。"
user_prompt = f"请根据以下文本内容，生成 {num_questions} 个不同的问题，这些问题都可以仅通过该文本内容来回答：\n\n{text_chunk}"
```

生成几个是超参，示例里取 3。于是一个 35 块的文档，入库后变成 35 + 35×3 = **140 条**。原来的检索是在 35 条里比，现在在 140 条里比。

然后匹配的对象换了：

- 原来是 **Q-K**（query 对 chunk）；
- 现在是 **Q-Q**（query 对 question）。

<span class="hl-red-bg">一个问题和一个问题之间的相似度，天然高于一个问题和一个答案之间的相似度。</span>这条几乎是常识，但它是 Q-Q 匹配有效的全部理由。

实测同一句 query：「中国政府对 AI 大模型发展有哪些支持的政策」——

- 纯文本匹配：相似度 **0.78**；
- 增强后：最高相似度 **0.94**，评估得分 **0.8**（基线是 0.5）。

top-10 检索结果全是 question 类型，把 k 提到 20 才看到 chunk，这也印证了问题条目的相似度整体更高。

## 三、拿到的是问题，用的是原块

这里有个必须做对的细节：**命中的是问题，塞进上下文的必须是问题背后的原文档块**。

所以入库时 metadata 要带上三样：`type`（chunk 还是 question）、`chunk_index`（第几个窗口）、`original_chunk`（原始块文本）。

组装时按类型分流：

```python
for result in search_results:
    if result["metadata"]["type"] == "chunk":
        chunk_indices.add(result["metadata"]["index"])
        context_chunks.append(result["text"])
    elif result["metadata"]["type"] == "question":
        idx = result["metadata"]["chunk_index"]
        if idx not in chunk_indices:          # 去重
            chunk_indices.add(idx)
            context_chunks.append(result["metadata"]["original_chunk"])
```

去重不是可选项：三四个问题可能指向同一个块，重复拼进去，上下文白长一截，token 白花。

整个流程还要配一个向量库的最小实现，`add_item / similarity_search` 两个方法就够，本质和 Milvus、ES 一样的接口。区别只在别人做了 ANN 索引。

## 四、意图识别：to B 交付的标配

企业知识库里有一类问题**一定不能错**：「董事长是谁」「早上几点打卡」「年假几天」。

这类问题不适合交给向量相似度去碰运气。做法是建一个 QA 库，配一个意图识别：query 进来先判断它是不是落在这些「必须准」的范围里，是就路由到 Q-Q 匹配，不是就走常规的 Q-K 检索。

这也是双保险的思路：

- 命中 QA 对，直接拿答案回来，甚至不用过大模型；
- 都不命中，再走文本检索那条路。

**query 库覆盖得足够全的时候，Q-Q 匹配的召回率能到 98% 以上。** 这个数字的前提很硬：覆盖率。覆盖率不到，98% 没有意义。

## 五、人工 QA 库：90%，但会过期

更极端的做法是不让模型生成问题，**人工写**。

流程是：把客服日志里用户真问过的问题全捞出来，去重，人工校验成一个尽量全的 query 集合，再一个问题一个问题写标准答案。

做成纯 QA 对之后，准确率能到 **90%**。

代价也很清楚：文档一变、政策一改，QA 库就得人工跟着改。**精度高，但耗时、可维护性差、灵活性低**。所以它适合「答案极少变动、错误代价极高」的场景，不适合知识天天更新的场景。

## 六、查询转换：改 query 而不是改库

前面几招动的都是右边——文档、块、QA 库。这一招动左边：**让用户的 query 变得更准、更全**。

检索是双塔结构，左手 query、右手知识库。改完右手，回头改左手。

三种改法：

| 类型 | 做法 | 例 |
| --- | --- | --- |
| 查询重写 | 把含糊的问题写具体、写详细，补充相关术语 | 「政府对 AI 有哪些支持」→ 补上算力、算法、产业应用等维度 |
| 后退提示 | 把具体问题泛化成更宽的问题，捞更广的上下文 | 「AI 大模型的支持政策」→「各国/全球的 AI 支持政策」 |
| 子查询分解 | 拆成若干聚焦不同方面的子问题 | 「有哪些政策」→ 财政的、法律的、科研的、国际合作的 |

子查询的实战例子是销售场景。用户问「这台车该怎么卖」，直接检索只能捞回一堆车的参数。拆成三个子问题就具体了：现在买有什么政策支持、这车本身好在哪、和竞品比优势在哪。

代码只改一段：**从 query 到 embedding 之间**。

```python
def rewrite_query(original_query, model="gpt-4o"):
    system_prompt = "你是一名擅长优化检索查询的AI助手。你的任务是将用户的查询改写得更加具体、详细，并包含有助于检索准确信息的相关术语和概念。"
    user_prompt = f"请将下列查询改写为更具体、更详细的表达，补充相关的关键词和概念，以便更好地检索到准确的信息。\n\n原始查询：{original_query}\n\n改写后的查询："
    return client.chat.completions.create(model=model, temperature=0, messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt}]).choices[0].message.content.strip()
```

退后和分解只是换提示词，结构完全一样。

这类改写还有一个大家天天在用、但不自知的例子：带联网搜索的对话产品，你在提问后看到的「思考中」过程，它搜的往往不是你那句话，而是若干条被扩写过的关键词。**那就是 query expansion 在跑。**

电商场景还有一层加法：把用户画像拼进 query。一个偏爱可爱风的用户搜「卫衣」，默写出来的是「卫衣」两个字，只有加上画像，才能捞到那些不带「可爱」标签但风格相符的商品。这就是**长尾搜索**问题，也是「大模型 + 推荐」现在最热的一个方向。

## 七、实测：原始 query 往往最好

四种都跑一遍，用同一个问题：「中国政府在 AI 上有哪些政策」。

结果出乎意料：**只有原始 query 的结果最好**，它把算力政策、技术政策等各方面都讲到了。

原因在这一句：**上下文能拼进去的 chunk 数是有限的**。改写、退后、分解各召回一批，混在一起就超了，超了就得截断，截断就可能把原本对的那块挤掉。信息引入得越多，噪音也越多。

<span class="hl-red">查询改写的收益不是单调递增的，它有一个拐点，过了拐点就开始掉。</span>

再叠加一个现实：改写本身不稳定。同一个问题，今天改写成一套词，明天换一套。这种不确定性在生产环境里是要付出评估代价的。

所以判断标准只有两条：

1. 用户原来问的是不是**大多数都不准确**？如果是，才值得重写。
2. 这个场景里有没有**专门的扩充逻辑**？销售、电商这种带行业词表和用户画像的，改写收益明显；通用问答就没必要。

简历上同时写「query expansion + 后退查询 + 查询分解」的，通常意味着把能想到的模块都堆上去了。**这类模块，最多写两个。**

## 八、混合检索：两列结果都不够

回到最开始那个裂缝：语义相关不等于能答。

补法是**同时用两把尺子量**：向量相似度（语义）+ 关键词重合（尤其是名词重合）。

Milvus 官方那个 demo 把它演得非常清楚：同一个 query「why do we study」，三种检索各给一列：

| 列 | 依据 | 排第一的 | 特点 |
| --- | --- | --- | --- |
| Dense | 语义向量 | Why we drink alcohol? | 句式像、用词像，语义近，但**答非所问** |
| Sparse | 关键词（BM25） | Why do we need to study? | 关键词重合最多，但容易被「do / study」这种噪声带偏 |
| Hybrid | 加权融合 | How do I study | 语义与关键词同时成立 |

<!-- 图 1 | https://milvus.io/docs/zh/hybrid_search_with_milvus.md | Demo 那张三列表格，重点截 Dense 列第一行 "Why we drink alcohol?" 和 Hybrid 列的排序差异 | 用来证明纯语义检索会把句式相似但内容无关的句子排到第一 -->

关键词那一列用的是 **BM25**，本质是 TF-IDF 的两个拳头：

- **TF（词频）**：某个词在这篇文档里出现得越多，得分越高；
- **IDF（逆文档频率）**：某个词在所有文档里越稀有，权重越高。

两者合起来的效果是：「的、在、去」这类到处都有的词，重合了也不加分；「机器学习」「算法」这类特有名词，重合一次就显著加分。BM25 自动把有信息量的词顶上来。

融合就是加权求和：

```
最终分 = α × 语义分 + (1 - α) × BM25 分
```

两个分数得先归一化到同一量纲再相加，否则一个是余弦值（0~1），一个是 BM25 原始分（可以很大），加权没有意义。α 是可调权重——**这就是简历上「动态权重的混合检索优化」里那个「权重」**。

动态的意思是：按意图分别调 α。问答类意图关键词权重要高一些，概念解释类意图语义权重要高一些。同一套参数通吃所有意图，通常不是最优。

混合检索现在已经不算「优化」了，它更像**标配**：单靠语义或单靠关键词，都会在某一类问题上系统性失败。

## 九、图检索：两者都召回不到的那些

还有一类问题，向量和关键词**都够不着**。

「张三和李四的关系是什么，他们共同参与了哪些项目？」张三和李四可能各自出现在不同的段落里，讲他们共同项目的那段，两个人名一个都没出现。这时候不管怎么算相似度、怎么碰关键词，都召回不到。

因为缺的不是「像」，是「关系」。

图数据库存的就是关系：节点是实体，边是实体间的关联。做法分五步：

1. **实体识别**：从 query 里认出张三、李四；
2. **关系识别**：判断是同事、管理还是负责；
3. **查图**：图里以三元组形式存储，找对应路径；
4. **多跳检索**：把张三连接的项目全列出来，李四连接的也列出来；
5. **生成**：把两份项目清单一起给大模型，它自然能答出共同负责的是哪个。

《倚天屠龙记》那个例子最直观。问「张无忌的感情史」，直接检索会把整本书里出现「张无忌」的段落全捞回来。而有了知识图谱，围绕张无忌连着赵敏、周芷若，把与这些实体相关的片段一起取回——<span class="hl-red">张无忌和赵敏在字面上、语义上都不重合，但在图谱里一跳就到了</span>。

医疗是最典型的落地场景。问「痛风应该用什么药」，只要识别出实体「痛风」，顺着「治疗方案」这条边找到对应的药，答案就出来了。而那个药名和「痛风」这两个字，在原文档里很可能根本不在同一段。

知识图谱建得足够完善时，这类问答的准确度能提到 **95% 以上**。前提也很硬：图得先建好，且覆盖你要问的关系。

## 十、分层检索：先查目录再翻页

库里混着保险、证券、银行各类数据的时候，还有一个更基础的问题：**检索空间太大了**。

问证券的内容，却从银行数据里捞回一批噪音——上下文被污染，而且库大、算得慢。

分层检索的思路和人查书一样：

1. **一级目录**：先看这个问题属于哪一章（章节有摘要，先跟摘要比）；
2. **小节**：进到那一章，再比哪一节的标题相关；
3. **chunk**：只在这一小节内部做向量检索。

一个具体例子：「深度学习在医疗影像中的最新应用和挑战」。第一层比章节摘要，命中第二章「诊断应用」和第三章「技术限制与挑战」；第二层只在这两章里比小节标题，命中「深度学习的准确率」和「多模态影像的融合」；第三层才进小节里做 chunk 级检索。

收益是双份的：**准确度提升**（噪音进不来）+ **效率提升**（要算的向量变少）。

一个实测口径：原来在 **54000 个片段**里检索，改成先查摘要再细化之后，**向量空间缩减 95%，响应时间提升 60%**。

分层的依据别按「文档超过 10 页」这种物理口径切，要按业务本身的层级切——章节、产品线、业务线，这样分出来的层才有语义。

## 十一、HyDE：先假装自己知道答案

最后一个是假设文档嵌入（HyDE）。它盯的是另一处错位：**问句 vs 答句**。

库里存的是答案，用户输入的是问题。这两者在向量空间里本来就不该长得像——一个在「问」，一个在「答」。

HyDE 的做法是：先让大模型**根据问题编一个答案**，然后拿这个假设的答案去检索。

逻辑很顺：假设答案和库里的真答案，都是在回答同一个问题，<span class="hl-red">它们之间的相似度，比问题和答案之间高</span>。这也就把匹配类型从 Q-Q 或 Q-K，换成了 **A-A**（answer 对 answer）。

| 匹配类型 | 谁和谁比 | 用在哪 |
| --- | --- | --- |
| Q-K | 问题 ↔ 文档块 | 常规检索 |
| Q-Q | 问题 ↔ 生成的问题 | QA 对增强 |
| A-A | 假设答案 ↔ 库里真答案 | HyDE |

注意它多了一次大模型调用——假设答案必须先生成出来。所以它同样是**用延迟换召回**。

HyDE、查询重写、意图识别这几个模块，简历上最多写两个。四个全写，等于告诉面试官「我没在真实流量下跑过」。

## 十二、这一层的取舍

这一篇的六种手段，其实在回答同一个问题的不同侧面：

- **QA 对 / 人工 QA 库**：改右边，让库长得像问题；
- **查询转换 / HyDE**：改左边，让问题长得像答案；
- **混合检索**：两把尺子一起量；
- **图检索 / 分层检索**：绕开「相似」这条唯一的路。

它们不互斥，可以叠：意图识别分流之后，每一条子链路用不同的组合。但叠的时候要记住那句在整门课里反复出现的话——<span class="hl-red-bg">没有一种优化是普适的，加不加只看评估集上的分数，以及你愿不愿意付那一段延迟。</span>

数字都绑着具体条件和文档：0.78 到 0.94 是一次示例查询的结果，98% 依赖 QA 库覆盖率，95%+ 依赖图谱完整度，54000 个片段的收益是特定场景。**换场景就要重测，不能直接引用。**
