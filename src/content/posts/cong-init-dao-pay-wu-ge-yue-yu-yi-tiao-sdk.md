五月的最后一周，我在开发环境里又跑了一笔转账。金额 **0.01 元**，收款方是我自己。截图存进交接文档，然后回后台把权限一项一项点掉：代码仓库、发布平台、监控看板、值班群。

这是 2025 年的 5 月。一年半之后回头再看这五个月，工位和值班群早就不在日程里了，但有几个细节还很清楚：那张流程图改到第三版才画顺；`pay` 阶段报错只回一句「支付失败」；离职那天我最后关掉的，是收银台的测试开关。

转入转出核心链路、收银台 SDK 接入、转账方式优化、数字证书组件、关键风控拦截。整齐到我自己回头读都要愣一下——五个月里，我在这些词之间来回跑的次数，比真正落地的功能多得多。

## 一、回顾链路

业务线前半部分几乎全是，雨燕+蚂蚁采集，后面才开始慢慢接需求。

「支付结算业务线」听起来很大，落到前端就是几个页面：转入、转出、收银台、证书、结果页。所谓**链路**，就是一笔钱从用户点下「确认转出」到后端记账之间，前端要依次经过的那些格子。

这段我花了两周才画清楚。画到第三版才想明白：流程图不是给自己看的，是给下一个接手的人看的。钱经过的每一格，都有人负责，也都有它自己的坏法。

## 二、学与做

落在我名下、能真正上线的改动主要有三块：转账方式优化、数字证书通用组件、延迟转账能力。剩下是一堆「参与」「支持」「配合」——评审会我坐在旁边听，发布单上我的名字在最后一行。

不是不想做，是支付链路不给。一个转账页面上的按钮改动，要走风控评审、灰度观察、值班表；我的权限只到预发环境，无法发布。实习生在这条链路上的位置，是看客和校对，不是作者。

所以后来跟人讲这段实习，我的说法一直很克制：学到的东西远多于做掉的东西。

<span class="hl-red-bg">五个月里我真正拿到的，是这条链路的「地图」——哪一格归谁管，哪一格容易坏，坏了先打给谁。</span>

这张地图比那三块功能值钱，可惜当时我不知晓。

## 三、SDK 三阶段

收银台是这段实习里最硬的部分。它的接入被拆成三段：`init` → `render` → `pay`。

- `init`：把2088、支付场景、是否走延迟转账这些配置交给 SDK，拿回一个实例。这一步错了，后面全是空的。
- `render`：把收银台 UI 挂到页面上。样式冲突、弹层被父容器裁掉、移动端键盘顶上来，都在这一段。
- `pay`：真正发起支付，回调可能由 SDK 抛，也可能来自页面跳回来。

边界看着清楚，实际最费时间的是「参数在哪一段丢的」。同一笔钱，`init` 里少一个场景标识，`pay` 阶段就换了另一条通道。

我当时干的活是把这些字段的来源一件件钉下来，整理成文档：

| 文档 | 谁在用 | 解决什么 |
|---|---|---|
| 转入转出流程图 | 新人、测试 | 看得懂钱从哪一步走到哪一步 |
| 接口清单 | 前后端联调 | 少问一句「这个字段谁给」 |
| 应急处置指南 | 值班的人 | 出事时先看哪、先找谁 |

这三份东西是我实习期最像「产出」的部分。不好看，之后还有人翻。

## 四、异步状态

Redux-Saga 是我在这五个月里唯一被逼着学到骨头里的东西。支付页面一屏可能挂着 **20 多个接口**，有的是顺序依赖，有的是并行的，有的失败了还能继续。

串行和并行的分界线很朴素：后一个的入参要不要前一个的结果。

```js
//示例代码 串行：限额要用账户信息去查
const account = yield call(fetchAccount, uid)
const limit = yield call(fetchLimit, account.no)

// 并行：三件事互不依赖，等最慢的那个
const [cert, risk, fee] = yield all([
  call(fetchCertStatus, uid),
  call(fetchRiskResult, uid),
  call(fetchFeeRate, payload),
])
```

真正难的是第三件事：**用户中途退出怎么办**。Saga 的可取消性是我第一次意识到「异步不是等结果，是管理一堆可能没人要的结果」。

另一件我带走的能力是「用户路径回调」。把用户在页面上的动作序列打进日志——点了哪个按钮、走到第几步、带了什么参数——线上报错时顺着反推，能定位到用户在哪一步停住。<span class="hl-red">这是这段实习里我唯一觉得「学到就是赚到」的东西</span>，后面几年我一直在用它，换了三套框架都没换这个思路。

## 五、风控展示

风控这一块我碰的是展示，不是判断。两件具体的事：

**关键词拦截**：转账备注里带敏感词，前端在输入框旁边给提示。真正的判定在后端，前端能做的是让人在被拒之前就知道为什么。

**贷款资金差异化展示**：同一笔转账，资金来源不同，页面上的提示措辞和要走的确认步骤都不一样。这种需求前端能做的不多，就是把「哪种情况显示哪一段」的分支捋干净，别在一个条件里塞五个变量。

<span class="hl-red">前端的风控是体验层，不是安全层。</span>这句话我在评审会上听过一次，后来每次写拦截逻辑都会先想一遍：我拦掉的是误操作，还是把自己当成了防线。

## 六、望乾师兄

感谢要具体，不然像客套。

教我最多的不是文档。是 code review 里那些不客气的批注——「这个 `yield` 写在外层，取消不了」「你这个 loading 是页面级的，用户会以为整页卡死」。也是值班时被问住的那几次，最后还是师兄垫底。还有入职一个月就让我做团队技术分享这件事，逼着我把会的东西写成结构，那次我讲了四十分钟，讲完手心是湿的。

## 回顾

现在有人问实习该怎么过，我会先给三条，谈不上建议，只是我事后补出来的顺序：

1. **先画链路图，别急着写组件。** 组件写到第三个就熟了，链路图不画，永远不知道自己在整条线的哪个位置。
2. **见到权限边界就问为什么。** 「这块为什么我不能改」是最快了解一个系统架构的问法，比读十页文档有用。
3. **把「参与」的活儿也做成文档。** 功能带不走，文档带得走。

离开那天最低的一笔转账是 0.01 元，收款人是我自己，备注写「测试」。它在我的账单里躺了很久，我一直没删。

那是我唯一能证明自己碰过这条链路的东西。
