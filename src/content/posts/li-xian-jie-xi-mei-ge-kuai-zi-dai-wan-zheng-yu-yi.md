切块是唯一一个「切错了，后面所有优化都补不回来」的环节。所以先从这里开刀。

## 一、固定长度切块切掉了什么

一段原文：「AI 是计算机分支的一个学科……它专注于……创建组成部分」。

按固定长度切，如果恰好拦在「这些机器」中间，拿到的那块是「AI 是计算机的学科到这些机器」——**后面的信息没了，「这些机器」这四个字还成了冗余**。

更隐蔽的是第二种情形：关键词检索命中「机器」，但「机器」被切到了上一块，于是系统拿上一块去回答。而要的那句话是「机器可以执行复杂任务、机器学习是 AI 学习的重要部分」，在下一块里。

<span class="hl-red">这种不规则的切块直接把语义切死了</span>：完整的表达被劈成两半，无论后面用向量还是用关键词，都只能捞到半句。

## 二、语义分块：句子级 embedding + 断点

做法分三小步：

1. 先把文本按标点切成完整单句，不再按固定字符数硬切；
2. 每个句子单独做 embedding；
3. 逐对算相邻两句的相似度——第一句和第二句、第二句和第三句……再设一个阈值，**高于阈值就把两句粘在一起，低于阈值就在这里断开**。

举个具体例子。第一句和第二句的相似度是 **0.85**（「AI 是个计算机学科，它专注于创造智能机器」），粘起来。第二句和第三句是 **0.45**，说明这里发生了语义转折，在中间切开，第三句另起一块。第三句和第四句是 **0.75**，粘。

这里有个极易讲错的地方：阈值**不是**「相似度最高值的 90%」。正确做法是把这一串相邻句的**不相似度（距离）排序，取第 90 百分位处的那个值**作为阈值。LlamaIndex 里对应参数是 `breakpoint_percentile_threshold`，默认 **95**。

代码里三种取法都给了：

```python
if method == "percentile":
    threshold_value = np.percentile(similarities, threshold)   # 相似度分布的第 X 百分位
elif method == "standard_deviation":
    threshold_value = np.mean(similarities) - threshold * np.std(similarities)
elif method == "interquartile":
    q1, q3 = np.percentile(similarities, [25, 75])
    threshold_value = q1 - 1.5 * (q3 - q1)

breakpoints = [i for i, sim in enumerate(similarities) if sim < threshold_value]
```

三种方法万变不离其宗：**用一种统计口径判断两句话语义是否连续，低于口径的地方断开**。差别只在阈值怎么定。

## 三、实测：分数从 1 掉到 0.5

切完是 **231 个块**（原来是 42 个）。接着照原样跑：embedding → 语义检索 → 组装 → 生成 → LLM 打分。

结果是 **0.5 分**，比固定切块的 1 分更低。

原因不复杂：<span class="hl-red">块变小了，而且只取 top-2</span>。语义分块后每块只表达一个语义，块更短，两段拼起来的信息量反而比原来那两块少。上下文信息变少，答案自然不完整。

这个结果真正要记的不是「语义分块没用」，而是：**换了一种分块方式，top-K 这个参数要跟着重调**。块变小、块数变多，k 还停在 2，等于自断信息。演示里 k 没有跟着重调，所以分数掉——这不是方法错，是参数没跟着改。

## 四、开销：真正劝退的地方

除了跑分，语义分块在工程上的问题是**贵**。

十几页的文档还能接受；上百页、几百页的文档，要按句子切分、每句都做一次 embedding、再两两算相似度，这个计算量和调用量会非常难看。

所以实际应用里，语义分块用得并不多。它的真正价值是提供一个**思路**，不是提供一个生产方案：

- 如果文档解析成 markdown，段落与段落之间天然有语义边界，靠 `#` 的标题层级就能分段，分段后做**段落合并**，块数变少、检索也会更快；
- 「页与页之间合并」「相邻段落合并」这些做法，都从这里借来的。

顺带一句：面试问到「语义分块怎么做」，标准答案就是「句子 embedding + 相邻相似度 + 百分位断点」，这一段能讲清楚，分数就拿到了。

## 五、chunk size：大块和小块各自的代价

固定切块有两个必须人为定的参数：`chunk_size` 和 `overlap`。

`chunk_size` 没有标准答案，**不一定大块就好，也不一定小块就不好**，得在你的场景里测。

大块的两个问题：

1. 上下文长度必然变大；
2. 一块里可能塞了好几种语义，做相关性检索时匹配得不够精准。

小块的两个问题：

1. 信息不完整；
2. 块数暴增，整条流程变慢。

一个直观的例子：原文从「人工智能是计算机的分支」一直讲到「模仿人类类脑神经网络的结构」——

- 用 **512 token** 切，切成 2 块；
- 用 **1024 token** 切，1 块就装下了。

1024 那块信息更全，但语义也被压成了一坨。所以块大小永远是「完整度」和「精准度」的拉扯，中间那根线要靠评估集去试。

## 六、overlap：50 到 100 token

`overlap` 解决的是「一刀砍在句子中间」的问题。

比如「通过算法使计算机能够从数据中学习并作出预测或决策」这句话被拦腰切断。用户问「通过计算能使得什么」，检索命中的是上一块，而上一块答不了这个问题。

加一段重叠就能救回来。用两句中文举例，切点在「通过算法」和「是计算机」之间：

```
overlap = 4：
- 机器学习作为人工智能的核心技术之一。通过算法
- 通过算法|是计算机能够从数据中学习并作出预测或决策。

overlap = 5：
- 机器学习作为人工智能的核心技术之一。通过算法
- 。通过算法|是计算机能够从数据中学习并作出预测或决策。

overlap = 10：
- 机器学习作为人工智能的核心技术之一。通过算法
- 心技术之一。通过算法|是计算机能够从数据中学习并作出预测或决策。
```

经验值：**overlap 取 50 到 100 token，大约是块大小的十分之一**。这样每个块的开头和结尾都能保住一小段完整语义，边界处的信息不会丢。

## 七、跑分一样时，选大块

做一个对比实验：把 chunk size 分别设成 **128、256、512**，切出 **326、164、82** 块，各自 embedding、各自检索、各自生成，然后用忠实度和相关性两个维度打分。

结果：**三种切法的分数基本一致**。

那该选哪个？<span class="hl-red">评估集足够完善的前提下，选大块。</span>

两个理由都在检索侧：

1. **省 token**：块大、块少，embedding 调用次数变少。326 次调用和 82 次调用，成本和耗时差四倍。
2. **省计算**：做向量检索时，query 要和库里每一条算相似度，库小了，计算次数也就少了，**端到端的首字延迟直接受益**。

首字延迟这个概念值得单独说一句：用户把 query 发上去，要等一段时间才开始收到第一个字。块数越少，这一步越快，用户感受到的「卡顿」就越短。

所以 **RAG 是一个系统性工程：除了准确率，还要算响应速度**。这也是为什么后面每次优化都要问一句「它加在离线还是在线」——离线慢不算慢，在线慢是真慢。

## 八、相邻块一起召回

检索命中一块之后，它的前后往往还在讲同一件事。

问「什么是机器学习」，命中那块讲的是机器学习本身，但它的前后讲的是「算法基础」和「深度学习」。只拿命中块去回答，信息偏窄；把前后一起拿回来，就有了「算法基础 → 机器学习 → 深度学习」这条链，既能答「什么是机器学习」，也能顺手答「机器学习和深度学习的区别」。

做法只多一步：拿到 top-K 的索引后，把索引两侧 `context_size` 范围内的块一起拼进上下文。

```python
start = max(0, top_index - context_size)
end = min(len(text_chunks), top_index + context_size + 1)
return [text_chunks[i] for i in range(start, end)]
```

注意返回的**块数量没变，变的是每块覆盖的信息变大**。代价是上下文变长，所以 `context_size` 一般取 1，别贪。

## 九、给每块起一个标题

每块原文有个通病：**块里全是离散细节，没有一句能概括它讲什么**。

用户问「介绍一下人工智能的基础」，而那一块通篇在讲学科定义、发展、分支，字面上没有「基础」二字——向量匹配未必命中。

解法是：切完块之后，**先让大模型给每块写一个凝练的标题**，然后把「标题 + 正文」一起送去做 embedding 和检索。

```python
def chunk_text_with_headers(text, n, overlap):
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunk = text[i:i + n]
        header = generate_chunk_header(chunk)   # LLM 生成一句标题
        chunks.append({"header": header, "text": chunk})
    return chunks
```

检索时两个分数取平均：

```python
sim_text = cosine_similarity(q, chunk["embedding"])
sim_header = cosine_similarity(q, chunk["header_embedding"])
avg_similarity = (sim_text + sim_header) / 2
```

结果：评估分数从 **0.5 升到 1**。

为什么有效？因为这模仿了人找资料的方式：<span class="hl-red-bg">人不会一头扎进正文里找答案，人是先看目录标题，判断这一章能不能答我的问题，再翻进去。</span>标题就是块的目录。

开销也可控：每块多一次大模型调用，大约是原流程两倍时间。**而它发生在离线解析模块，用户根本感知不到**。这就是离线模块可以奢侈的理由。

## 十、命题分块：让每句话自包含

更激进的做法是命题分块（propositional chunking）。

问题：切完之后每一句并不能独立表达完整语义，得放回整段才有意义。比如「1996 年……近年来深度学习快速发展，AI 广泛应用于金融、交通等领域」——如果单独切出「AI 广泛应用于金融、交通等领域」，没有「近年来」这个时间限定，语义就变形了。

做法是让大模型在切块时**把上下文一起看**，把省略的主语和关键限定补全。四条规则：

| 规则 | 含义 | 反例 |
| --- | --- | --- |
| 只表达一个具体事实 | 自己能表达完整语义 | 一句话里塞三个结论 |
| 用全称而非代词 | 拆分后要有实体主语 | 「那个地方特别好」，不知道指哪 |
| 补上时间/限定词 | 原文的「近年来」「2024 年」要带下来 | 只留「AI 广泛应用于金融」 |
| 只含一个主谓关系 | 避免并列、复合句，匹配更准 | 「A 提升了效率并降低了成本」 |

代价很直白：39 个块拆成 **1425 个命题**，其中第 36 块单独拆出 44 个命题。**每分一次就要调一次大模型**，耗时和资源消耗都很大。

好处是召回几乎不会带进不相关的块，精度很高、检索效率也高。所以它只在**文档量不大、但精度要求极高**的小场景里，配合意图识别一起用，不作为通用方案。

## 十一、多模态：统一进文本流水线，或者统一进向量空间

知识库里不只有文字，还有表格、图片、视频。两条路。

**路线一：一切转成文本。** 图片用 OCR，或者用多模态大模型直接描述（caption）；音频用 ASR；视频先抽音轨再用 ASR，或者按帧让多模态模型描述（一帧大约 1/25 秒，具体看帧率）。转完之后，**后面的流程和纯文本完全一样**。

```python
def generate_image_caption(image_path):
    base64_image = encode_image(image_path)
    response = client.chat.completions.create(
        model="llava-hf/llava-1.5-7b-hf",
        messages=[{"role": "user", "content": [
            {"type": "text", "text": "Describe this image in detail, focusing on its academic content:"},
            {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{base64_image}"}}]}],
        max_tokens=300)
    return response.choices[0].message.content
```

这条路的价值在 PPT 上体现得最明显：很多企业的资料是 PPT，里面有大量流程图，OCR 只能读出零散文字，读不出「谁指向谁」。《Attention Is All You Need》那张架构图就是典型——纯文本描述不了它的数据流，多模态模型可以。

**路线二：多模态 embedding。** 用 CLIP 这类模型把图片直接映射到语义空间，图文共用一个空间，然后在这个空间里「找朋友」。这种还能顺带做**以图搜图**。

两条路都发生在**离线解析模块**：一个是把图片描述塞进文本分块里，一个是在向量化阶段分开编码、存进同一个空间。跟在线链路没关系，所以慢一点、贵一点都还能接受。

## 十二、这一篇的净结论

离线模块的判断标准只有一条：**它慢不慢，用户看不见；它错没错，用户一定看得见。**

所以这里的优化空间最大：块标题值得做（0.5 → 1，两倍时间换一倍的准确率）；chunk size 值得测（跑分一致就选大块，省 token 省延迟）；overlap 值得调（1/10 是个好起点）；语义分块和命题分块要谨慎（前者换参数才有效，后者成本高到只能定点使用）；多模态在文档含图表时是刚需，纯文本库里不必上。

下一篇往在线链路走，那里的规则要反过来：**每一步都要算延迟，因为没有一步是免费的。**
