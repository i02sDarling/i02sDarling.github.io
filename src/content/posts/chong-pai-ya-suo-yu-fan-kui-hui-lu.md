检索回来的东西，往往不是最终答案该用的东西。在线链路的收尾，就是把它们挑一遍、压一遍、记住了下次别再算一遍。

## 一、重排解决的是排序错位

前面三篇都在改「召回什么」，这一篇改「召回之后怎么排」。

到这一步，文本分块、向量化、query 向量化都做完了。但检索是靠**向量相似度**直接判断的，光靠它不太够——用户提问的那句话和真正的答案，向量未必长得特别像。

一个日常例子：用户问「怎么退货」，正确答案那一段写的是「申请售后流程」。两句话意思一样，向量相似度却不一定高。

结果就是：**真正相关的知识排在后面，甚至没进 top-K**。

既然第一次检索已经给每条结果打了分，那就可以在这个分数基础上**再打一次分、重新排一次序**，把真正能回答的顶到前面。

| 阶段 | 类比 | 干什么 |
| --- | --- | --- |
| 向量相似度检索 | 海选 | 先粗略捞出「可能相关」的一批 |
| 重排序 rerank | 复赛精挑 | 再仔细看谁真正相关，重新排队 |

重排有两种，很多人以为重排就等于「上一个 rerank 模型」，其实不是——尤其金融、法律这类垂直场景，通用 rerank 模型的效果未必好。

## 二、规则重排：用 metadata 重新打分

第一种是**基于规则的重排**。

检索回来的结果里，metadata 存着结构化信息：来自哪一章、哪一页、哪个产品线、什么时间。这些信息不参与 embedding，但可以参与打分。

流程是两步：

1. 先快速捞出相似度高的一批，比如 **top 30**；
2. 对这 30 条做一轮深度规则重排——用 metadata 里的字段加权，相关的往前挪，时间不对的往下压。

<span class="hl-red">这种方式极其常见，效果也相当好</span>，因为它便宜：不需要过任何模型，纯计算。

规则可以非常朴素：同一章节加 0.2、同一文档名加 0.1、年份不匹配直接扣分。规则写得越贴业务，效果越好。这也是「混合检索 + 规则重排」能合成一带的原因——规则吃的不一定是文本，也可以是 metadata。

## 三、模型重排：把 query 和文档拼起来看

第二种是 rerank 模型。要理解它，先理解原来的向量检索是什么结构。

**bi-encoder（双编码器）**：query 过 embedding 模型变成一个向量，chunk 过**同一个** embedding 模型变成另一个向量，然后算两者相似度。这也是「query 和文档必须用同一个 embedding 模型」的原因——只有同一个模型，它们才落在同一个向量空间里。

这种做法的短板是：两段文本各自编码，**谁也看不见谁**。它只能比较「两个向量近不近」，不能判断「这段能不能回答那一段」。

**cross-encoder（交叉编码器）** 换了做法：

1. 把 query 和文档**拼成一段**，中间插一个 `[SEP]` 分隔符，告诉编码器这是两个文本；
2. 整段送进编码器，直接**输出一个相关性分数**；
3. 对这 30 条逐条重复，得到 30 个新分数，重新排序。

关键是：**一次只吃一对**，不是把 30 条一起塞进去。所以 30 条候选就要跑 30 次。

一个小例子，query 是「怎么退货」，库里 10 万条，快筛后取前 3：

- A「售后申请流程」向量分 0.72
- B「退货政策说明」向量分 0.70
- C「物流发货时间」向量分 0.68

cross-encoder 逐条打分之后：`怎么退货 [SEP] 售后申请流程` 得 **0.95**，`[SEP] 退货政策说明` 得 **0.93**，`[SEP] 物流发货时间` 只有 **0.10**。C 在向量阶段分不低，但它被看穿了。

## 四、三笔账

| 方案 | 准确率 | 计算成本 | 说明 |
| --- | --- | --- | --- |
| 无重排 | 可能 60% | 很低 | 检索回来直接答 |
| 规则重排 | 略升（10 个命中 7 个） | 很低 | 规则不过模型，速度极快 |
| 模型重排 | 更高 | 较高 | 每个 query 和每条 chunk 都要过交叉编码器 |

模型重排贵在哪？贵在**召回阶段第一次要经过模型**。

原来算相似度是不经过模型的：embedding 早在离线阶段就算好了，在线只做向量点积，纯数值计算。上了 cross-encoder 就不一样了，top 30 就要跑 30 次模型推理。

而且并行也有上限：不可能为了这一个请求起 10 个编码器副本。资源大的时候 chunk 可能有几十万条，候选取 50、100 也常见，这个乘数会更难看。

结论不是「别用」，而是**要算清楚这笔账**：<span class="hl-red">重排基本都能提点，提多少和贵多少是两个必须分开回答的问题</span>。

## 五、大模型重排：小模型、长上下文、只输出 index

还有第三种：让大模型来排序。这里有几个容易做错的工程细节。

**第一，用的一定是小模型。** 相对小、速度非常快。因为它干的是「打分」，不是「回答」——判断两段像不像，比把答案写出来简单得多。

**第二，它的上下文要长。** 要能一口气吞下大量候选，把相关的挑出来，再把结果交给慢而强的模型去生成。

**第三，输出一定不是文本，是 index。** 让它输出「第 3、第 7、第 12 条」这种索引，输出短，速度快。如果让它把相关段落抄一遍，提速的努力全白费。

```python
def rerank_with_llm(query, results, top_n=3, model="gpt-4o"):
    system_prompt = """你是一名擅长评估文档与查询相关性的专家。
    根据文档对查询的回答程度打分，0-10 分：0-2 完全无关，3-5 部分相关但不直接回答，
    6-8 相关且能部分回答，9-10 高度相关且能直接回答。
    只回复一个 0 到 10 的整数，不要其他文本。"""
    scored = []
    for r in results:
        resp = client.chat.completions.create(model=model, temperature=0,
            messages=[{"role": "system", "content": system_prompt},
                      {"role": "user", "content": f"查询：{query}\n\n文档内容：\n{r['text']}\n\n请打分："}])
        score = float(re.search(r"\b(10|[0-9])\b", resp.choices[0].message.content).group(1))
        scored.append({**r, "relevance_score": score})
    return sorted(scored, key=lambda x: x["relevance_score"], reverse=True)[:top_n]
```

这段 for 循环是为了讲清楚逻辑，**实际不会这么写**。生产上是一次把所有候选连索引一起给进去，让它直接返回相关索引。

顺带一个额外收益：重排会把不相关的文档丢掉，交给大模型的上下文更干净，最终回答质量也会跟着上来。

## 六、关键词重排：中文要先分词

还有一种开销不小但确实有效的做法：**按关键词重合度重新打分**。

逻辑很直白：每命中一个关键词加 0.1；如果这个词出现在文本前四分之一，说明它更可能是主题词，再加 0.1；按词频再加，最多 0.2。最后 `基础分 + 关键词分` 重新排序。

中文的坑在分词。英文按空格切就能拿到词，中文不行——「机器学习」切成「机器」「学习」，语义就变了。所以要引入 **jieba**：先过滤掉长度为 1 的词（「的」「了」这类没信息量的），再比 query 和 chunk 的重合词。

这条路和 rerank 模型一样，**开销都很大**，但在特定场景（专有名词多、编号多、型号多）里比语义重排更稳。

## 七、RSE：中间那块要不要并进去

相关段落提取（RSE）解决一个细节问题：命中的块之间，语义是断开的。

比如检索回第 1 块（0.8）和第 3 块（0.9），中间第 2 块没进 top-K。但第 2 块讲的是承接两边的内容，把它加进去，上下文就完整了。

怎么判断第 2 块该不该加？答案是一个刷题时会遇到的算法：**最大子段和**。

第一步，给每块算一个值：**相关性分数减去惩罚项**。不相关的块（相似度低于某个值）会被减成负数。

第二步，拿五个块举例：`0.8、0.6、0.9、-0.7、0.2`，从头往里加，找和最大的连续段：

- 0.8 + 0.6 = 1.4，变大；
- 再加 0.9 → 2.3，继续变大；
- 再加 -0.7 → 1.6，变小了；
- 再看块 5 是 0.2：1~5 合计 1.8，**不如 1~3 的 2.3**，所以扔掉块 4、5，返回 1、2、3。
- 如果块 5 是 1.0，1~5 合计 2.6，就把 1~5 全拼起来。

停下来的条件有两个：达到最大块数上限；或者后面再也找不到更大的连续段。

第三步，按原始文档顺序把这段拼回去，保持上下文顺序和逻辑关系。

## 八、上下文压缩：8000 变 1200

如果检索回来的上下文太长，还有一个收尾手段：压缩。

做法是用一个本地部署的小模型，把检索回来的内容做 summary，压到 **1200 个 token**。收益是三条同时改善：

| 指标 | 原来（8000 token） | 压缩后（1200 token） |
| --- | --- | --- |
| 成本 | 0.024 美元/请求 | 0.005，约五分之一 |
| 响应时间 | 8~12 秒 | 2~3 秒 |
| 相关性比例 | 30% | 95% |

相关性从 30% 涨到 95%，是因为压缩本身就是一次信息提纯——原来的上下文里七成是不相干的废话，压完只剩能回答问题的部分。

代价当然也有：**压缩一定损失信息**，损失多少取决于压缩策略和模型质量。这是一个明确的 trade-off，不是免费午餐。

这个方向现在很热：ICLR、EMNLP 每年都有大量「上下文压缩 / 提示词压缩」的论文，目标都是同一件事——用更少的 token 保住最关键的信息。

## 九、三种压缩，三种力度

压缩放在哪一步？就在**上下文拼接阶段**：重排在拼接之前，压缩在拼接之中。

三种压缩方式，本质是三种「怎么删」：

1. **选择（select）**：从 10 个块里挑最相关的 5 个，其余不传。压缩率 **63.8%**。
2. **总结（summary）**：把 10 个块合成一段摘要，只传摘要。压缩率 **79%**，压得最狠。
3. **句子抽取（extract）**：把 10 个块当成一整篇，原样抠出与 query 相关的句子，以句为单位传进去。压缩率 **71.8%**。

原始上下文长度都是 **10018 字符**，压完之后剩下三成到两成。

```python
def compress_chunk(chunk, query, compression_type="selective", model="gpt-3.5-turbo"):
    # selective：只保留能回答 query 的句子，保留原措辞
    # summary  ：写一段只与 query 相关的摘要，中立、事实性
    # extraction：只抠原句中与 query 相关的句子，用换行分隔
    ...
    return compressed_chunk, compression_ratio
```

批量压缩在代码里是 for 循环，生产上完全可以并行。

## 十、什么时候该压

三个场景：

**一是碰上上下文长度上限。** 有些模型窗口就是有限（比如 3 万多 token），超了就得处理：把大块切成三段、分别总结、合并，再交给回答模型。

**二是 Agent 的记忆模块。** 多轮对话不断往上下文里塞，一方面会超限，一方面会拖慢响应。做法是设一个阈值，比如超过 2000 token 就触发一次 summary，用新摘要替换旧记忆。这一步可以和回答**同步进行**，不额外增加用户等待。

**三是成本已经压不住的时候。** 上游 token 花得太多、延迟太高，压缩就是最直接的止血手段。

## 十一、反馈回路：把好答案存成缓存

到这里，链路本身已经完整。最后一个模块让系统**自己变好**。

思路：用户查询 → 检索并回答 → 用户打分（相关性、质量，1 到 5 分）→ 高分结果直接构造成 QA 对入库存起来。

下一轮如果命中了这条高质量回答，**连长上下文都不用传，甚至不用过大模型**，直接把答案返回。

这就是一个缓存：35 条变 45 条这种数字看着不起眼，但只要命中了，那一次请求的成本和延迟几乎为零。原来 35 条的向量库，加进 10 条高质量问答之后变成 **45 条**。

```python
def fine_tune_index(current_store, chunks, feedback_data):
    good_feedback = [f for f in feedback_data if f["relevance"] >= 4 and f["quality"] >= 4]
    for f in good_feedback:
        text = f"Question: {f['query']}\nAnswer: {f['response']}"
        new_store.add_item(text, create_embeddings(text), {"type": "feedback_enhanced"})
```

这条链的实测现象是：第二轮比第一轮更快，有时只需要命中那一个 QA 块就拿到最终结果。

反馈回路是**一体两面**的：正向是「把好答案攒起来」，反向是「把差答案找出来，定位是哪一环的问题，再改」。后者才是系统工程的主体，这一篇讲的 20 个优化点，本质上都在为反向服务。

## 十二、它会坏在哪

反馈回路有两个硬前提：

**质量**。存进去的必须是真正的好答案。质量高，性能与准确度一起涨。

**数量**。query 覆盖到场景里的大部分问法，才会形成系统性提升；只覆盖少数几种，就只是在那几种上有效。

还有一个必须警惕的反例：**如果一条差答案被打了高分、存进了库，下一轮它会以「命中缓存」的身份被直接返回**——错误被固化了。

所以它真正需要的是**自动评估 + 自动优化**的闭环：入库前先过一遍自动评测，不合格的不许进。这就是「自我净化的 RAG」。

## 十三、自适应检索：不同意图走不同路

还有一类问题不是「检索得准不准」，而是「该不该用这套检索」。

同样是提问：

- **简单事实问答**：直接向量检索、拼上下文、回答，一条路走完。
- **总结类**：「帮我总结第三章」——这句话和第三章的内容在语义上几乎不可能相似，向量检索必然失效。这时候该做的是**用 metadata 把第三章的所有块捞出来**，拼成一个长上下文去总结。

所以要先分流。工业系统里常见做法是分 6 个意图，每条子链路**配两样不同的东西**：检索策略不同、最终提示词不同。

一个真实例子：产品对比。用户问「你这个开关和别的开关有什么区别」。向量检索只能找到讲公牛开关性能的那段——它不知道「别的开关」是谁。而如果产品存在图数据库里（节点是产品，边是关系），就能顺着关系把**有连接关系的其他品牌开关**一起捞出来做对比。

|  | 向量检索（语义） | 图数据库（关系） |
| --- | --- | --- |
| 擅长 | 找「意思像」的文本 | 找「有关系」的实体 |
| 本例能拿到 | 讲公牛性能的段落 | 和公牛有关联的其他开关 |
| 短板 | 不知道「别的开关是谁」 | 需要先建好关系图 |

分流之后的效果：只在某一个子链路里做针对性优化，整体提升能到 **30%、42%、35%** 这个量级。反过来，如果不管意图把优化全叠上去，某条链路的优化手段放到另一条链路上，**效果不升反降**。

## 十四、80% 的天花板

意图识别有一个务实的数字：**即使用当前最好的模型，意图识别的准确率也就 80% 左右**，提示词写到极致也很难超过 90%。

这是这条路线的天花板，也是它最尴尬的地方——分流错了，后面所有优化都白做（分流到总结链路，实际是个事实问答）。

解法是微调：**在这个任务上，小模型微调反而比大模型零样本更准**。意图识别是「分类」任务，标签体系明确、样本可以造，非常适合做小而专的模型。

顺带一句判断：在问答主模型上做微调，收益通常很小，多数时候还不如直接调 API；而**在一个子模块上做小模型微调**，含金量高得多。

## 十五、Self-RAG：两个判断

Self-RAG 出自一篇论文，思路是给链路加两个「要不要」的判断。

**第一个在 query 向量化之前**：这个问题到底要不要检索？

「今天天气怎么样」这种常识问题、闲聊、假设场景，检索纯属浪费——embedding 要做、相似度要算、上下文要拼，全是开销。判断不需要，就直接交给模型答。

**第二个在相似度检索之后**：召回的内容和 query 相关吗？

如果全都不相关，就别拼进上下文了，**让模型自己回答**。因为把一堆无关文档塞进去，Transformer 的注意力会被这些噪音带偏，答案反而更差——这一点只要试过一次就能感觉到：给模型一份完全不相关的资料，它答得比不给资料还糟。

| 位置 | 判断什么 | 不满足时 |
| --- | --- | --- |
| query 向量化之前 | 要不要检索 | 不检索，直接回答 |
| 相似度检索之后 | 召回内容和 query 相关吗 | 全不相关，让模型自己答 |

两个模块都很轻，各一次小模型调用。用得不多，但思路值得记住：**不是所有问题都需要走完整链路**。

## 十六、动态纠正

最后一个：如果本地知识库压根检索不到相关信息，怎么办？

做法是加一个 reflect 模块，对检索结果做反思：如果判定这些文档都回答不了问题，就**回落到网络检索**，去外面找资料。

它和 Self-RAG 的第二个判断是同一个位置，只是动作升级了——Self-RAG 是「不相关就让模型自己答」，动态纠正是「不相关就上网找」。

## 十七、评估：人定尺子，LLM 当助教

最后一个问题：这套东西怎么评估？

先澄清一个常见的误解——「用 LLM 评估 LLM 的输出，是不是套娃」。

不是。因为两个模型的角色完全不同：

|  | 生成答案的 LLM | 评估答案的 LLM |
| --- | --- | --- |
| 干什么 | 回答问题 | 按标准打分 |
| 依据 | 检索回来的上下文 | 人为写好的评估规则 |
| 需要知道正确答案吗 | — | **不需要** |

生成的是「照资料答题的学生」，评估的是「按标准批卷的助教」。<span class="hl-red-bg">助教不需要会做这道题，只要照尺子打分就行——真正定尺子的是人。</span>

尺子怎么定？流程是固定的：

1. 选一个 query 方向；
2. **人工构造 100 个 query**；
3. 让系统把 100 个都跑一遍，答案都答出来；
4. **人工先评估这 100 个结果**；
5. 看哪些维度要达标——有效性、无害性（harmlessness）、完整性；
6. 据此写一套评估规则，让规则覆盖场景需求；
7. 把规则当提示词交给大模型，让它按规则评。

评估方式上，规模化以后通常是**抽样 + 自动**：造 1 万组评估数据，人工评一部分，剩下的交给 LLM 按同一套规则评。

维度上不止端到端。**检索召回率要单独算**：提前构造好 ground truth 的「正确召回块应该是哪些」，然后用逻辑直接算命中率。端到端分数掉了，召回率没掉，说明问题在生成侧；两个都掉，问题在检索侧。这个区分能省掉大量排查时间。

## 十八、收尾

在线链路的所有优化，其实都在同一张账单上：

- 重排：多一次（或 30 次）模型调用，换排序更准；
- 压缩：多一次 summary，换 token 更少、延迟更低；
- QA 对 / 反馈缓存：换命中即返回，但要求覆盖率；
- 意图分流：多一次分类，换每条链路的参数更贴场景；
- Self-RAG / 动态纠正：多两次判断，换「不该检索时不检索」。

<span class="hl-red">没有一个优化是免费的</span>，所以判断一个方案该不该留在生产环境，只有两个依据：评估集上的分，和账单上的延迟、token、运维成本。

这也是整套 20 个优化点真正想要传递的东西：**它们不是一份必做清单，而是一张地图**。地图不会告诉你该走哪条路，但能告诉你每条路通向哪里、要花多久。

所有数字都绑着具体条件——ada-002、gpt-4o 与 gpt-3.5-turbo 混用、35 块与 140 条的样本量、单次示例查询。**换文档、换模型、换场景都要重测；引用的每一个收益数字后面，都应该跟着「在什么条件下测的」。**
